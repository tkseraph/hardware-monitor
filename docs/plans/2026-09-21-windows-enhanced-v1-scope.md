# Windows 首版增强指标范围与采集组件方案

日期：2026-09-21。代码基线：b83391d，feat/windows-support。本文是范围与实施方案，不表示指标已接入。

用户已明确：首版就要进程磁盘 I/O 和更多温度指标，可以接受另行设计需授权的采集组件。因此不能把普通权限受限的指标自动排到下一版。此选择是范围确认，不等于已经同意安装某个服务或驱动；本轮未提升权限、未安装或运行第三方传感器组件。

## 首版范围

| 能力 | 首版要求 | 展示与边界 |
| --- | --- | --- |
| 进程实际磁盘 I/O | 必须实现全系统进程读/写 B/s，支持分别排序 | 使用存储事件口径，不把一般进程 I/O 当纯磁盘吞吐；提供采集丢失及无法归属状态 |
| CPU 温度 | 目标为当前 Ryzen AI 9 HX 370 的一个经过核实的封装/控制温度 | 保留传感器真实含义；不把热区温度、逐核温度或 Tctl 偏移值混为同一指标 |
| GPU 温度 | 目标为当前 Radeon 890M 的已验证 GPU 温度 | 热点温度若可用可另列；不复用 CPU 温度来补 GPU 缺值 |
| 内置磁盘温度 | 目标为当前两块 NVMe 的合成温度 | 历史绑定匿名设备身份；不同传感器不得按枚举顺序猜配 |
| Windows 磁盘健康状态 | 纳入，按每块系统磁盘设备显示 | 明确是 Windows 报告的正常/警告/异常/未知，不等于 SMART 全通过或寿命百分比 |
| SMART/NVMe 警告、磨损、通电时间 | 纳入读取与展示能力，按设备支持程度返回 | 字段各自允许未知；不将未知显示为 0；不据健康正常显示“寿命 100%” |
| USB/外置盘温度与健康 | 有有效来源且确认映射时展示 | 当前新增 Kingston USB 设备不是温度完整支持的验收基线；不因驱动未暴露字段宣称硬件无传感器 |

首版温度的验收基线限定这台 Windows x64、该 CPU/GPU 与两块内置 NVMe，不承诺所有 Windows 设备。若核心目标（进程磁盘 I/O 或上述任一主要温度来源）确实不可取得，须报告具体阻塞和替代方案，由用户重新决定范围，不能自行把“暂无数据”算成全部验收通过。磨损、通电等可选设备字段则按支持状态验收。

不纳入本轮首版范围：风扇控制、超频、功耗限制、寄存器写入、电压调整、SPD、全主板传感器、远程监控、进程终止、逐文件 I/O 明细、文件路径历史以及进程明细的七天存储。

## 已核实的依据

2026-09-21 普通权限只读查询明确选择字段，未查询序列号或文件内容：

- MSFT_Disk：两块 NVMe 和一块 USB 设备均返回 HealthStatus=0；OperationalStatus 返回 53264。
- MSFT_PhysicalDisk：对应设备返回 HealthStatus=0、OperationalStatus=[2]。两类对象的 OperationalStatus 编码不同，不能共用一张枚举表。
- MSFT_StorageReliabilityCounter：CIM StatusCode=2，消息为“无法从客户端中访问 CIM 资源。”MI_RESULT_ACCESS_DENIED=2；没有读到温度、磨损或通电值。此结果不是“设备不支持”。
- 先前内核磁盘 ETW 探针返回 ERROR_ACCESS_DENIED=5，未启动会话。该证据来自前阶段，本轮没有重跑跟踪会话。
- GetProcessIoCounters 的统计覆盖进程全部 I/O，因此不能替代纯存储事件指标。

以上只验证了来源可见性，没有更改应用 DTO、界面或硬件。系统当前有 USB 设备，不将其与早期“两块 NVMe”的机器快照混为矛盾记录。

来源：[MSFT_Disk](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/msft-disk)、[MSFT_PhysicalDisk](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/msft-physicaldisk)、[MI_Result](https://learn.microsoft.com/en-us/windows/win32/api/mi/ne-mi-mi_result)、[GetProcessIoCounters](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters)。

## 采集方案

### 1. 进程磁盘 I/O：Windows 内核 ETW

使用独立 Rust 采集组件，限于实时磁盘读写及完成归属所需的最小进程/线程事件。事件必须按版本及指针宽度解码；通过发起线程和进程生命周期关联到 PID + 创建时间，不能直接把完成事件头中的进程当作发起者。启动时已有进程/线程需建立基线，短命线程、PID/TID 复用和不能归属的事件需明确处理。

显示为“进程磁盘读取/写入”，以实际观测窗口计算 B/s；不承诺与某个系统界面的每个瞬时数值完全一致。缓存命中、延迟写回、分页及系统代执行 I/O 都会影响归属，归到 System 或未知的事件不得重新猜给原应用。内部允许未归属汇总，不在产品中编造“未知 PID”。

启动、重启、唤醒后先建有效窗口。只在覆盖完整且映射可靠时允许真实零；丢事件/缓冲溢出显示不完整状态，不能作为完整排序结果。进程退出、无法读取身份和缺少首个基线均不能伪造 0。

只输出聚合读写值、创建标记、观察窗口、质量计数和状态。ETW 会话不写 ETL 文件，不订阅文件名事件，不输出文件路径、内核地址或原始事件。未归属与丢失计数用于解释覆盖率。保留原有整盘吞吐作为独立来源，不通过各进程相加替代它。

依据：[DiskIo](https://learn.microsoft.com/en-us/windows/win32/etw/diskio)、[DiskIo_TypeGroup1](https://learn.microsoft.com/en-us/windows/win32/etw/diskio-typegroup1)。

### 2. 磁盘温度、磨损与通电：先系统存储接口

在授权的采集组件中先验证 Storage Reliability Counter 或关联方法能否正常返回。如果只读 WMI 来源不足，再验证白名单的 NVMe SMART/Health 查询；不先引入通用硬件驱动。

温度使用来源定义的摄氏度；直接 NVMe 字段按其规范转换 Kelvin。Windows Wear 表示已使用磨损程度，100 表示估计磨损限度，并非“剩余寿命”；NVMe Percentage Used 与通用 Wear 保留来源区分，不强行截到 100。PowerOnHours 转为足够宽的整数，记录原始字段宽度，识别溢出/来源限制，不根据时间差补算通电量。来源之间不静默切换同一历史口径。

优先沿 MSFT_Disk 已确认的映射/关联获取数据，再与持有设备句柄的匿名历史身份核对；不能认为 MSFT_PhysicalDisk.DeviceId 一定等于系统盘号，更不能按型号和容量合并。

健康摘要按来源展示；警告字段可同时存在多个。显示“Windows 状态正常”不等于无故障保证。来源失败保留最近有效观察时间并标记过期，不能刷新旧值的时间戳。

依据：[Storage Reliability Counter](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/msft-storagereliabilitycounter)。

### 3. CPU/GPU 温度：传感器兼容性验证

CPU 优先评估 LibreHardwareMonitorLib；GPU 可评估同一库或 AMD ADLX 的温度能力接口。ADLX 必须先检查本机支持标志并核实适配器映射，不能从 SDK 有该 API 推断 Radeon 890M 一定提供温度。

本轮官方最新 release 链接解析为 LibreHardwareMonitor v0.9.6，发布说明包含 PawnIO 模块及安装器变化。它只是候选版本：后续必须锁定 tag/commit、依赖和散列，审核实际选用版本的传感器访问路径、签名、驱动安装行为及许可证，再进入本机授权试验。不使用滚动 nightly 作为交付依赖，也不自动降级到旧的内核驱动。

采用独立 .NET sensor host（若最终选用 LHM），只启用 CPU/GPU 与确需的存储读取，默认关闭主板 EC/SMBus 扫描、控制器和所有写控制入口。第三方库暴露的写入能力不能透传到产品接口。官方说明部分传感器需要管理员权限；CPU/GPU 在本机可读性仍待验证。

该库声明 MPL 2.0，另有第三方许可；发行前整理 notices、修改源码义务和依赖许可。此处是依赖审查任务，不替项目自行选择整体开源许可证。

来源：[LHM README](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor)、[v0.9.6 发布记录](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/releases/tag/v0.9.6)、[ADLX 官方性能监控头文件](https://github.com/GPUOpen-LibrariesAndSDKs/ADLX/blob/main/SDK/Include/IPerformanceMonitoring.h)。

## 权限、安装与退出

主界面保持普通权限。第一轮实现采用按需启动的授权辅助进程，不先安装常驻高权限服务。用户选择“启用增强采集”后启动组件，退出软件时停止自身 ETW 会话和子进程；关闭窗口到托盘则继续采集。组件未启用时基础指标继续工作，界面区分未启用、需授权、预热、不支持、失败和过期。

组件间使用本机命名管道、固定协议版本和限定指标命令。创建时设置调用者 SID/登录会话 ACL，拒绝远程客户端，检查对端进程及会话，使用一次性握手；身份校验不能仅靠随机管道名或客户端自报 PID。帧长、行数、采样间隔及队列都有限制。接口不接受任意执行文件、脚本、DLL 路径、驱动操作、设备写命令或文件读取请求。传感器配置来自编译期白名单，不加载用户提供的插件路径。

辅助程序/驱动在正式交付时必须位于具备适当写权限保护的位置，加载已核验依赖，不能宣称从任意用户可写目录运行的高权限组件具有可靠防篡改保证。实际部署位置、签名和安装程序在安装前落成可审阅清单。

ETW 组件用独立随机会话名，只清理自己创建的会话。UI 异常退出后组件以受控心跳/断连超时退出并尝试 StopTrace；崩溃残留会话的识别、回收和重新启动要单独测试，不停止其他应用跟踪会话。

若 LHM 实测需要安装 PawnIO 等内核组件：先列出确切来源、版本、哈希、签名、许可、将创建的服务/驱动、是否重启、已有组件是否共享、卸载规则，再请求安装授权。授权辅助进程与安装驱动是两个不同动作。不会关闭内存完整性/驱动阻止策略来使候选组件运行；兼容性失败按阻塞处理。

## 采样和历史

| 数据 | 首版周期目标 | 历史策略 |
| --- | --- | --- |
| 进程磁盘事件 | 后端持续消费，约 1 秒聚合，进程页约 2 秒刷新 | 只保留有限内存窗口，不保存进程明细历史 |
| CPU/GPU 温度 | 2 秒起步，后台 5 秒 | 新增明确的指标 ID 与传感器身份，沿用七天分层历史及连续段 |
| 磁盘温度 | 5 秒，后台可降低至 15 秒 | 已有 disk.temperature 接口需实际接入来源，不只开放图表 |
| 健康/磨损/通电 | 60 秒及设备连接变化时 | 首版展示最新快照；不以秒级频率反复保存静态值 |

周期为实施目标，须测量开销后确认。ETW 与传感器分别隔离，任何一个超时不阻塞 CPU/RAM。辅助组件的数据由主进程验证并写历史，保持只有主进程写 SQLite。传感器重建或来源切换均分段；不能沿用旧时间刷新显示为新值。

## 分步实施与完成标准

1. **E1：组件协议与假来源。** 实现本机管道、身份与消息校验、有限队列、状态/退出协议；默认不开高权限，也不依赖传感器驱动。测试错误身份、畸形帧、断线、UI 退出、采集阻塞以及同机器多隔离实例。
2. **E2：授权只读来源验证。** 准备可执行辅助程序、确切权限与限时参数后请求运行授权。先验证 ETW 事件解码/归属和存储可靠性字段；同时完成 LHM/ADLX 源码及依赖审查。输出脱敏能力矩阵。此阶段不自动注册服务或安装驱动。
3. **E3：进程磁盘 I/O 集成。** 使用自建短命子进程和有界临时文件测试读写、缓存、PID/TID 复用、进程退出、丢事件及无法归属；对照相同时间窗的独立存储计数器，记录误差和归属限制。网络-only 操作不得冒出本地磁盘字节。完整过滤/排序后分页，数据不完整时提示。
4. **E4：温度与健康集成。** 本机 CPU、GPU、两块 NVMe 逐项确认传感器语义、单位和身份；至少三次低频观测并与独立工具对照。先完成无需新驱动的路径；若 CPU 等核心目标仍依赖驱动，单独走上述安装审批与兼容验证。
5. **E5：整体验收。** 主 UI 不提升权限；拒绝/撤销增强采集仍能看基础指标；退出无自身会话残留；模拟源失败和实际一次批准的睡眠恢复正常；界面指标、历史与告警状态一致；安装升级卸载的组件行为写入 W7 交付清单。

E1 可以直接进入开发。E2 需要在具体程序和操作已准备好后请求授权；现在不请求抽象的“全部管理员权限”。本文完成的是第三步范围决定，应用新增功能仍需按 E1–E5 实施。
