## W0 环境和高风险来源调查

**目标：** 在大规模修改之前，确认原生开发条件，以及 GPU 和进程存储读写是否有符合要求的来源。

1. 复核工作树和提交，开始实施时新建独立开发分支；已有分支先检查。保留本轮基线和 Mac 已知未验项目，更新旧 README 中的阶段性表述，不把 Mac 记录覆盖成 Windows 结果。
2. 核实已有 Rust MSVC、C++ Build Tools、Windows SDK、WebView2。Rust 候选先参考旧构建记录 1.97.1，核实 Windows 可用性后固定具体版本及 rustfmt/clippy；已安装兼容版本可先验证，不自动批量更新。缺系统组件时列明组件和用途，再安排安装。Windows 所需条件以 [Tauri 前置条件](https://v2.tauri.app/start/prerequisites/)为依据。
3. 核对锁文件下载和构建兼容性，沿用 Node 24.19.0/npm 11.17.0 作为本机起点；类型检查和构建通过后才确认为 Windows 基线。同步 engines、工具版本文件和 CI，不只固定本地终端。
4. 设计小范围、显式执行的只读探针，输出允许字段：来源、适配器类别、指标语义、单位、权限、状态、实际时间窗、耗时和脱敏结果。GPU 先调查 DXGI、GPU Engine/GPU Adapter Memory 的可用实例及关联；进程存储 I/O 先调查普通权限来源，ETW 如需额外权限只记录限制。
5. 为两项高风险能力分别给出结论：可在普通权限实现；仍需验证；或需要用户决定权限/范围。API 返回成功不等于有有效数据；系统工具能显示也不等于该值可以通过同样的公开接口取得。

**产物：** 建议新增 `docs/windows-environment.md`、`docs/windows-capabilities.md`、`docs/windows-metric-contract.md`。这些文件当前尚未创建；探针源码与合成夹具可入库，本机原始输出不入库。

**验收：** 明确 MSVC target；依赖版本可追溯；高风险指标各有候选、统计范围和下一步验证方法。若缺工具或接口权限不满足，只暂停相关步骤，其他独立工作继续。

## W1a 平台边界与原生编译

**目标：** Windows 能编译和启动诚实的空态，同时保留 Mac 实现。

1. 从 `sampler.rs`、`storage.rs`、`processes.rs`、`instance.rs`、`loginitem.rs`、`termination.rs` 抽出平台实现。建议保留现有 Cargo 工程，新增 `platform/mod.rs`、`platform/macos` 和 `platform/windows`；共享 DTO、历史、查询、设置和调度留在共享层，暂不拆成多个 crate。
2. 使用 `#[cfg(target_os = ...)]` 收口模块、导入和测试。仅使用 `cfg!(...)` 包住运行分支，不能消除不适用平台的类型检查。Windows API 依赖放在 target-specific dependencies；保留 Mac 的 IOAccelerator 聚焦查询和 Dock 恢复逻辑。
3. Windows 骨架对未实现来源返回明确状态；CPU/RAM 可以暂为 null，GPU 暂为带状态的空清单。前端同步最小改动，不能用默认 0 满足旧必填 DTO。稳定命令名与 camelCase 参数映射。
4. 先用绑定规范化数据目录的独占文件锁实现唯一写入者，评估 LockFileEx；句柄由应用状态持有。第二实例最小行为为明确提示后退出，完整激活流程留到 W5a。锁错误与“已有实例”必须区分。
5. 先建立独立的测试数据根，并核实 WebView 用户数据和 debug 日志的实际位置。`MONITOR_DATA_DIR` 只覆盖现有后端目录，不能据此声称全部隔离。必要时用独立开发标识及 WebView 存储配置隔离 UI 设置。
6. 将 Unix 子进程测试按平台保留，并准备跨平台专用测试子程序。默认测试不枚举本机进程、不注册自启；硬件集成显式选择，进程操作测试仅使用自建一次性子进程。需要外部命令时先修复有界输出、超时、截断状态和回收，Windows 子命令保持隐藏窗口。
7. 在 CI 中加入 Windows 原生检查，同时保留 Mac 检查。先构建前端再进行依赖 frontendDist 的 Rust release 构建，全部使用锁文件。配置文件已写入与云端已运行成功分开记录。

**产物：** 平台模块、必要依赖锁定、最小 Windows 状态界面、CI 修改、编译阻塞清零记录。

**验收：** Windows `cargo check --locked`、类型检查、已有前端测试通过；适用的共享与平台单元测试通过；原生窗口能够显示状态。Mac 编译与共享回归须在 Mac/CI 运行；没有执行就保留待验，不能以 Windows 成功代替。

**回退：** 撤回本阶段代码提交并恢复成套前后端契约，不迁移用户库。骨架成功仅标为“可编译”，不标为“Windows 基础版本完成”。

## W1b 数据契约与来源调度

**目标：** 每个指标独立表达可用性与新鲜度，慢来源不拖累快速来源。

1. 在共享 DTO 中区分能力与当前读数状态。能力至少覆盖未实现、未验证、支持、不支持、不适用和权限要求；读数覆盖预热、有效、失败、过期。保留上次值时同时返回原观察时间和当前错误原因，不能刷新旧值的时间戳。
2. 每个可空指标约定 value、unit、scope、source_id、observed_at、sample_interval/window、状态与脱敏原因。数值 0 只表示实际测得零。GPU 结构演进为适配器数组；模型、图表、历史对象 ID 同步迁移。与平台相关的说明由契约驱动。
3. Rust 后端继续拥有采样，不让 `get_system_info` 触发采样。把 CPU/RAM、GPU、磁盘吞吐、拓扑、健康分为独立来源；同一来源只允许一个在途任务。静态清单在启动/变化时读，必要的兜底刷新低频执行。
4. 主要动态指标保持前台 1 秒、后台 3 秒；温度建议 5 秒起步，健康/通电 60 秒，均需按来源实测调整。每次差分使用单调时钟的实际间隔。超期后跳过已错过的时刻，禁止无休止追赶或叠加新任务。
5. 阻塞 Win32/COM 调用使用有界执行单元；明确 COM 初始化线程及句柄销毁位置。超时等待不代表底层调用被取消；对不能安全取消的调用设计在途上限、降频和退出策略，必要时才研究受控子进程隔离。
6. 历史只接收新产生的有效样本，每个来源保留实际观察时间。组合快照中缓存的旧 GPU/温度值不能每次 CPU 更新时重写为新记录。来源故障与历史写入故障分别报告。

**验收：** 注入 GPU 错误、磁盘超时和拓扑失败时 CPU/RAM 继续更新；30 秒后台周期不会被固定 15 秒规则误报过期；预热/重置后不产生峰值；队列和在途任务有上界；生产入口无模拟数据。新字段直接测试生产序列化和前端消费代码。

## W2 CPU、内存和进程内存

**目标：** 第一版普通权限真实采集，覆盖 CPU、RAM 和进程内存排行。

1. 先按锁定版 sysinfo 验证 Windows CPU 刷新、总量归一化和最小刷新间隔，必要时补充原生 API。启动、长中断和来源重建后先建立基线；本机应验证 24 个逻辑处理器映射，其他硬件按枚举结果处理。
2. RAM 分开安装量、系统可使用总量、当前可用和当前已用。优先验证 sysinfo 与 GlobalMemoryStatusEx 的对应关系；不复用 Mac active/wired/compressor 公式，不拿进程工作集总和替代系统内存。
3. 进程表保留名称、PID、创建标记、明确口径的内存和 CPU。核实 sysinfo 的 Windows 内存字段究竟对应工作集还是其他统计，并按实际含义标注。系统表与受限进程分开处理，不因一行拒绝访问丢掉整个列表。
4. PID 身份优先使用可靠创建时间，避免仅靠低精度时间戳；通过同一进程句柄读取有关信息时管理其有效期。保留全量过滤、排序后分页和未知值排末尾。进程 CPU 必须说明整机归一化还是单核为 100%。
5. 进程明细建议页面可见时每 2 秒刷新，其他时候暂停额外枚举；后端合并过密请求。恢复后重新预热，不保存进程明细历史。

**验收：** 普通权限窗口连续更新；CPU/RAM 与系统工具在相近时间窗及可比口径下对照；明确缓存、工作集和任务管理器算法差异，不能要求逐拍完全相同。覆盖进程退出、PID 重用、首次样本、排序分页和受限进程。实际温度、频率、核心效率分组尚未验证时不加入猜测值。

**产物：** Windows CPU/RAM/进程基础来源、对照摘要、生产纯函数测试和只读集成测试入口。

## W3a 设备身份与历史隔离

**目标：** 真实磁盘和 GPU 历史接入前，解决重启、同型号设备、地址复用造成的串线风险。

1. 把匿名注册表持久化到有效数据根，使用版本化结构及随机生成的本地 ID；稳定哈希若用于查找，选择明确算法和格式，不能把 DefaultHasher 的输出当持久协议。
2. 将本轮设备地址、匿名设备身份、连接代次和历史序列键分开。历史键采用匿名 ID 加必要代次，不能只把 generation 放进 DTO 却不用于历史边界。CPU 核拓扑改变也要避免把旧 coreN 无条件接到不同逻辑处理器。
3. 不能只靠型号、容量和盘号证明同一设备。同型号同时在线的设备必须分配不同身份；跨重启没有足够信息确认的设备标记关联不确定并开启新系列。若要让用户手动确认历史关联，作为后续可选设计，不自动合并。
4. 不读取序列号作为解决捷径，不把设备实例路径/LUID 直接作为外发身份。确需在内存中寻址的系统标识仅留在来源边界，报告使用别名。无法可靠认定“同一块盘”的情况应明确记录，这不是仅靠落盘一个计数器就能解决的问题。
5. Windows 使用全新本地库，不导入 Mac 真库。旧 `dev-*` / `gpu0` 序列需要迁移时保留为旧来源系列，不按新枚举猜配。注册表损坏时保留原文件、生成新身份并提示，不能从头编号后撞上旧历史。

**验收：** 持久化往返、重启顺序改变、同型号两盘、盘号复用、热插拔、注册表损坏、不同数据根、多 GPU 和来源重建夹具。可证明的身份延续；不能证明的身份开启新系列；历史不交叉污染。

**回退：** 同时保留注册表和数据库的一致备份。已写新 schema/身份的库不得直接交给旧二进制；回退版本时使用对应备份或新的隔离目录。

## W3b 物理磁盘、卷与吞吐

**目标：** 以物理盘组织页面，准确表达卷、共享池和读写性能。

1. 建立完整拓扑 DTO，至少包含物理盘、分区、卷、池和关联边。Mac APFS 保留为平台类型；Windows 不构造假 APFS 容器。共享或未知归属的卷独立呈现，不能只返回磁盘数组而丢失关联对象。
2. 静态清单优先验证 Storage/CIM 或原生接口；卷到盘的映射评估 IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS，处理可变长度、多 extent 和访问受限。该接口描述的是一个卷在一个或多个磁盘上的位置，不能假定一卷一盘。[Microsoft 卷映射文档](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-ioctl_volume_get_volume_disk_extents)
3. 卷容量评估 GetDiskFreeSpaceExW，区分用户可用空间、卷空闲空间、用户配额和物理容量；不能拿配额相关总量当全盘物理大小，也不能把不同口径直接相减。存储池上的文件系统已用量不要按盘平均分摊。[Microsoft 容量接口文档](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw)
4. 动态吞吐优先验证 PDH PhysicalDisk。正确关联计数器与本机磁盘编号，排除 `_Total` 重复累计；不从盘符或实例名称猜物理身份。普通权限失败时记录原因，不自动提升权限。
5. 来源内部保留 bytes 和实际秒数；UI 明确 B/s、十进制 MB/s，容量按现有格式明确 GiB/TiB。读/写单独存值，总吞吐由同一有效窗口计算。沿用 `disk.throughput` 的原语义，新增读写历史必须同步 query 白名单、写入、类型与图表。
6. 拓扑低频缓存与设备变化刷新；吞吐每轮独立采集；温度失败不影响容量和吞吐。保留 ZHITAI/致态优先的展示排序，仅当实际存在该设备时生效。

**验收：** 本机实际磁盘/卷与系统清单对照；夹具覆盖无盘符、多挂载点、跨盘卷、Storage Spaces、虚拟盘、USB、未知映射和同型号两盘。没有实机的拓扑只标为模型/夹具通过，不宣称硬件兼容。默认利用正常活动观察吞吐，不安排写盘压测。

**产物：** 完整拓扑模型、Windows 存储来源、容量计算测试、身份关联和历史写入证据。

## W4a GPU 全局指标

**目标：** 正确识别 Radeon 890M，在虚拟适配器共存时提供可解释的全局利用率与内存。

1. 用 DXGI 核实适配器清单，再与系统清单关联；区分硬件、软件、远程/间接显示适配器及未知类型。基于接口属性、能力和映射选择默认可观测 GPU，不按名称黑名单或枚举第一项选择。本机虚拟显示驱动保持现状。
2. 验证 GPU Engine/GPU Adapter Memory 的可用性，建立适配器 LUID、引擎和实例映射。PDH 优先使用语言无关的英文计数器接口；通配符展开、动态实例、首次无数据和每个数据项的有效状态都要处理。成功添加计数器也可能尚无实例。[Microsoft PDH 文档](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhaddenglishcounterw)
3. 先确认每个计数器覆盖哪些进程/引擎，再定义去重和聚合。拟采用“最忙引擎代表整卡利用率”时，写明这是经本机验证后的展示口径，不直接把全部引擎百分比相加后截到 100%。微软曾说明任务管理器采用最忙引擎口径，仍需核对本机可用来源。[Microsoft GPU 统计说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)
4. GPU 内存分别记录可验证的专用/预留、共享使用量和相关容量/预算。集显的专用统计不代表独立显存芯片。全局内存不能把所有进程的含共享资源用量简单相加；没有正确分母就展示有效字节值。
5. `QueryVideoMemoryInfo` 提供调用进程的预算与用量，不能用于满足整机 GPU 内存目标。若只取得这一来源，GPU 全局内存仍是缺口。[Microsoft QueryVideoMemoryInfo 文档](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)
6. 界面支持按实际硬件适配器切换并使用正确历史身份。驱动重置、无实例、会话变化和适配器消失后清理句柄、重建基线；错误仅作用于对应来源。

**验收：** 用正常运行的其他图形程序作对照，确认反映的是监控器之外的活动；记录权限、驱动、时间窗与统计方法。夹具覆盖虚拟适配器排在首位、多硬件 GPU、实例重复、无实例和重建。只识别型号不能通过 V-04/V-05。

## W4b 进程存储 I/O

**目标：** 实现系统范围的进程存储读写排行，保留进程与物理磁盘吞吐的统计差异。

1. 根据 W0 结果确定来源，核查 sysinfo Windows 底层实现及候选原生接口。`GetProcessIoCounters` 文档定义为进程所有 I/O 的统计，不能直接填入 `disk_read_bps` 和 `disk_write_bps`。[Microsoft 进程 I/O 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters)
2. 如果普通权限只取得一般 I/O，可增加独立的明确字段和标签，但 D-010 的存储排行仍为未完成。普通权限无法取得纯存储统计时，输出三种可评估路径：继续研究来源、单独授权增强采集、用户明确调整验收范围。
3. 若评估 ETW，先核实事件确为所需存储活动、可归因字段、权限、事件丢失和缓存影响。仅读取必要字段，不落盘文件名、访问路径或命令行。仅管理本应用创建的会话；遇到已有同名会话不可停止或接管。额外权限验证在对应授权后进行。
4. 使用进程实例身份维护差分，处理首次值、计数回退、读取失败、进程退出与 PID 重用。枚举、过滤、排序和分页继续沿用已修复规则；同名进程不自动合并。
5. 对存储活动和纯网络/管道活动分别做隔离验证，测试程序与流量范围先明确；可优先用自建临时夹具与本机回环通信，任何额外负载单独安排。结果要说明是逻辑存储 I/O 还是实际物理 I/O，不要求进程总和等于物理盘吞吐。

**验收：** 来源语义与 UI 相符；非存储活动不冒充磁盘；未知值不按 0 排行；进程明细不入设备历史；完全退出后无本应用 ETW 会话或子任务残留。无法达到存储范围时只阻塞该项和基础整体验收，不阻止其他独立步骤。

## W5a Windows 桌面生命周期

**目标：** 关窗继续采样，恢复窗口不重复创建来源，明确退出能回收全部任务。

1. 检查 Windows 托盘图标、左键恢复、Show/Quit 菜单、任务栏最小化和恢复。可见但失去焦点的窗口保持前台策略；隐藏或最小化进入后台策略。通过实际样本间隔验收，不能只检查布尔变量。
2. 完成同一数据根的第二实例激活协议，保持 W1a 的唯一写入锁。可评估受限本地 IPC；若采用命名管道，限制为当前用户和对应数据根，只允许固定的激活消息。没有必要引入通用远程命令接口。
3. 同目录重复启动恢复既有窗口，第二进程退出；不同隔离目录可分别运行。测试路径大小写、别名/联接后的等价性和权限范围；跨用户目录权限失败不应触发共享数据访问。
4. 新增取消与关闭流程：停止调度、停止接收新历史写入、有限时间内完成已接受批次、释放 PDH/COM/锁、回收自身子任务。不得通过全局进程名查杀结束相关程序。异常退出后，下次启动应恢复，不依靠遗留 PID 文件判断存活。
5. 接入 Windows 电源/会话变化通知，配合超长间隔检测重建差分基线。使用注入时钟与事件测试；实际自然睡眠/恢复单独记录，不主动睡眠、重启或中断远程会话。
6. 自启使用 Windows 的每用户机制，启动路径取已安装 exe，正确处理空格和 Unicode。保持默认关闭、注册/查询/保存分开。实际注册测试由用户启用后完成，退出/卸载只清理本应用的注册项。

**验收：** 显示→最小化→恢复→关窗→托盘恢复→重复启动→退出的完整流程；持续历史和采样器数量正确；正常退出无自身任务残留；模拟唤醒后不出现速率峰值。真实自启和自然睡眠未执行时单列待验。

## W5b 历史、设置与界面回归

**目标：** 保留已有功能，修正跨平台契约变化影响的历史与存储行为。

1. 保留 SQLite 的 raw 1 小时、10 秒桶至 24 小时、60 秒桶至 7 天，以及当前事务守恒测试。新增指标和身份变更用明确 schema/契约版本迁移，在临时库和一致备份上先验证。主库、WAL、SHM 合并计算预算，读取大小失败不能默认为无限可写。
2. 超过 512 MiB 预算时停止新增历史并显示原因，保留实时查看和已有历史；预算包含写入/检查周期的可解释余量，不能宣称绝不瞬间越界。测试忙、满、损坏、checkpoint 失败和恢复，不通过清空用户库自救。
3. 消除后端 uniform stride 丢峰值/末点的问题，并在后端抽稀前保留真实缺口信息。建议新增版本化历史响应：保留时间和值，并提供分段/覆盖率/实际粒度；迁移前端后保留旧查询兼容入口，不能悄悄改变原命令返回结构。
4. 缺口阈值随来源周期与历史粒度变化；聚合桶里的局部缺失不能画成完整覆盖。大量分段时仍限制响应体积，必要时明确返回更粗的覆盖信息，不能因硬性点数上限而把断点连起来。原始采样若为 500 ms，检查秒级时间戳是否会合并/丢弃同秒值，定义显式聚合或毫秒精度方案。
5. 保留温度图的一小时范围、摄氏度刻度、至少 20°C 跨度、键盘与悬停读数。区分原始采样点和后端聚合点；将旧 `history-helpers.mjs` 镜像测试迁到生产 TypeScript 函数，避免只测试副本。
6. 设置保存采用并发安全的唯一临时文件、明确的替换行为和错误传播；验证已有文件反复覆盖、共享占用、只读目录、中文/空格路径、坏文件保留。失败时 UI 不能显示“保存成功”。
7. 明确语言和主题的持久化来源。建议本阶段保留主题首帧 localStorage 读取，把语言的 settings/localStorage 双来源收敛成有迁移规则的一套流程；不要无关地重做所有设置。测试隔离覆盖后端、WebView 和日志各自目录。
8. 平台名称、APFS、统一内存和 SIGTERM 文案按平台/能力展示。保留已有浅色、深色、跟随系统、中英文、ZHITAI 排序、窄窗口、reduced-motion 和无模拟数据空态。测试常见 Windows 缩放比例及屏幕间切换。

**验收：** 临时数据库完成迟到、重启、时间回拨、计数重置、7 天边界和存储故障测试；1/3/30 秒及低频传感器图表正确；设置/主题/语言重启可恢复；旧 Mac 共享功能通过回归。加速时间测试仅证明保留逻辑，不能算真实运行了 7 天。

## W6 优先增强指标

**目标：** 在基础版本稳定后逐项增加温度、通电时间和健康，不让传感器成为所有基础指标的依赖。

1. 先验证普通权限可用的 Windows 存储查询/可靠性来源，按 CPU、GPU、每块磁盘分别建立能力记录。来源没有读数时区分无权限、未实现、未验证和不支持，不能推断硬件没有传感器或风扇。
2. 温度核实单位转换，通电核实字段宽度和单位，健康区分 SMART 摘要、NVMe Percentage Used 与厂商定义。不能直接把 SMART 通过标成寿命 100%，也不把任意原始值做 `100 - value` 后显示为剩余寿命。
3. 按来源成本设置低频刷新并缓存静态健康信息；失败只影响相关增强项。新增历史指标时按 W5b 完整接入，不只添加曲线入口。
4. 如普通来源不足，再形成 LHM、厂商接口或独立组件的选型说明：预计能新增哪些指标、依赖和许可、运行权限、驱动初始化行为、维护与安全状态、HVCI/签名兼容性、退出与卸载。候选名称不等于已经选定或安装。
5. 服务/驱动若确有必要，先完成可审阅的具体方案，再由用户授权实际安装；主 UI 保持普通权限。组件只开放限定的只读指标接口，具有调用者验证与会话回收，禁止开放任意命令和硬件控制。

**验收：** 每一个新增读数都能说明来源、单位、范围、权限和实机结果；关闭增强后基础指标继续更新。温度/健康无法安全读取时保留明确限制。功耗、电压、SPD、风扇等额外项目按单独指标任务推进，不打包承诺全支持。

## W7a 集成和稳定性

**目标：** 把自动测试、Windows 实机和 Mac 回归结果分开记录，并确认安装交付之前的基础缺口。

1. 将既有 V-01～V-21 转为 Windows 场景，按下表逐项记录通过、失败、未执行和阻塞。测试直接覆盖生产适配边界、生产 DTO 和查询链，不在测试里重写一套判断。
2. 在隔离目录做至少 10 分钟轻量观察，包含前台、后台和页面切换；再安排 2 小时运行。真实 7 天观察另列开始/结束时间、版本、重启与缺口，不把多个版本的运行拼成一段连续成功。
3. 统计主进程、WebView2、探针/增强组件构成的完整进程树，记录整机归一化 CPU、工作集/私有内存、线程/句柄、来源耗时 P50/P95、样本间隔、失败/过期次数、队列与历史文件总增长。避免共享页重复统计后冒称物理占用。
4. 原计划的前台平均 CPU 2%、后台 1%、内存 250 MiB 可作为待复核的优化参考，不自动作为 Windows 已承诺 SLO。用连续趋势判断资源问题，先建立本机基线再决定预算；两点内存上涨不能单独证明泄漏。
5. 运行 Windows/MSVC 与 Mac 的共享检查和各自平台检查。Mac 无可用实机/CI 结果时保留发布前待验；跨编译或静态检查不替代 Mac 实机生命周期回归。

**产物：** 建议新增 `docs/windows-acceptance.md`、`docs/windows-resource-observation.md`，更新 Windows 能力矩阵。只共享允许字段和汇总，不提交进程命令行、序列号、完整探针输出或真实库。

**验收：** 基础指标各有实机动态证据；模拟故障不冻结其他来源；前后台节奏和退出行为满足约定；基础缺口未解决时报告为部分实现。2 小时和真实 7 天的完成状态各自独立。

## W7b 安装与交付

**目标：** 先交付可在当前用户范围安装的 Windows x64 包，并将二进制与真实测试结果绑定。

1. 先验证 release exe，再使用 Windows 专用 Tauri 配置生成 NSIS 安装包。建议首版仅 NSIS，不沿用 `targets: all` 同时承担 MSI 路径。Tauri 的 NSIS 默认安装当前用户，不需要管理员权限；WebView2 缺失时的安装方式仍要单独验证。[Tauri Windows 安装包文档](https://v2.tauri.app/distribute/windows-installer/)
2. 明确 WebView2 策略：开发机先使用已存在的运行时；交付前决定离线引导程序或联网引导方式，记录依赖、体积和缺失时行为。不把开发机恰好具备运行时当安装流程已验证。
3. 在 Windows 配置中核实产品名、版本、图标、目标架构、包标识和每用户安装范围。补齐 Cargo 中仍为空或模板值的作者、仓库、许可等元数据；项目自身的许可证由用户决定，不自行替项目选择开源授权。
4. 新建 Windows 发布脚本及可信清单生成流程：核实源码快照和工作树→逐项运行检查并验证退出码→构建版本化暂存目录→验证内层 exe/资源/架构→生成哈希和清单→完整校验后交付该目录。上一版包及其清单成套保留，不只替换一个安装包文件。
5. 清单包含 source commit、dirty（含未跟踪源码）、锁文件 SHA-256、版本、target triple、工具版本、测试通过/失败/跳过数、实际签名状态、exe 和安装包哈希。开发脏树产物可记录但不冒称干净发布；正式交付优先从固定干净提交构建。
6. 在用户选定的测试位置验证安装、重复安装/升级、启动、托盘、退出、卸载和重新安装；安装后不依赖开发终端、Node 或 Rust。默认保留历史，卸载处理本应用自启项；不能删除共享 WebView2 或其他软件组件。旧 schema 的回退遵循一致备份流程。
7. Authenticode 未做就标为未签名；签名证书与服务是另行决定的分发事项。公开推送、创建 Release、上传资产由用户另行指示。本地包、真实数据和日志不进入源码提交；共享前检查所有待推送提交的新增内容及文件名。

**产物：** Windows x64 安装包、对应 manifest、SHA-256、安装/退出/自启/卸载说明、实际支持矩阵、残余限制和回退说明。

**验收：** 包内 exe 能在 Windows 普通用户会话中独立运行；版本/哈希/测试/源码一致；安装和卸载结果有记录；Windows 签名状态明确。未跑真实 7 天、自然睡眠或自启实测时如实列为未验，不借用 Mac 结果补齐。

## 每次开发任务的完成方式

开始时核对当前提交、工作树和上一步验收，不重复执行已经有证据的工作。一次任务优先只处理表中的一个阶段；较大的 W1b、W3b、W5b 可以再按契约、来源、界面和测试拆成连续小任务。

每次结束报告本阶段改动、实际测试及退出结果、真实采集证据、未完成项、下一步依赖。代码和前后端契约成套提交；数据库迁移、设备身份和发布脚本分别保留可回退边界。需要安装、额外权限、真实自启或长时间负载时，先把具体组件、用途、影响和待验证结果写清，再处理所需授权，其他已可进行的工作继续。

建议先执行 W0，完成工具链缺项与 GPU/进程存储 I/O 的调查；随后执行 W1a 和 W1b。第一份可运行 Windows 增量以 W2 的真实 CPU/RAM/进程内存为里程碑。完整基础版本仍须覆盖 W3、W4 和 W5，并完成 W7 的对应验收。
