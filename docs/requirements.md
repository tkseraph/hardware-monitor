# 本机硬件监控软件：需求与决策

状态：12 项产品决策已确认；当前仅调整计划，不进入开发或新增采集探测。先完成本机 Mac，Windows 延后。
更新日期：2026-09-11。

## 1. 用户明确提出的目标

- 长期目标是支持 macOS 和 Windows 的本机硬件实时监控；当前优先完成本机 macOS，Windows 在 Mac 全部跑通并通过验收后再考虑启动（D-012）。
- 至少覆盖 CPU、GPU、内存、硬盘四类核心硬件。
- 总览页同时呈现各类核心硬件的关键状态；分项详情页呈现更详细的状态。
- 风扇监控为可选功能；若支持，可在总览页一并展示。

## 2. 期望指标清单

此清单记录用户目标，不表示所有硬件与系统组合均已验证可采集。

| 硬件 | 总览页目标 | 详情页额外目标 |
| --- | --- | --- |
| CPU | 名称、温度、总占用率 | 每核占用率、大小核分组、频率、电压、功耗 |
| GPU | 名称、温度、总占用率、显存占用率 | 引擎占用、显存用量、功耗、电压、频率 |
| 内存 | 名称、温度（适用时）、总占用率 | 频率、时序、电压、SPD、温度、物理内存总量/已用/可用、进程级占用 |
| 硬盘 | 名称、温度、使用率（分盘）、通电时间 | 读写 MB/s、活动时间%、平均响应时间、队列长度、进程级读写、总容量/已用/可用/未分配、温度历史曲线、寿命磨损/健康度 |
| 风扇（可选） | 风扇状态，具体字段待确认 | 待确认 |

详情页还需保留对应硬件的核心状态。

## 3. 需要核实的跨平台约束

以下是设计时必须考虑的差异，不是针对具体设备的采集验证结果：

- 指标可用性受系统版本、芯片/设备型号、驱动、连接方式和权限影响。
- Apple Silicon 使用统一内存，不能直接套用独立显卡“专用显存已用/总量”的语义。
- 内存 SPD、时序、电压、温度，以及部分 CPU/GPU 传感器数据，不能假定所有设备都会开放。
- 存储温度、通电时间和磨损数据可能依赖 SMART/NVMe 健康信息；外置转接桥、RAID、驱动和权限可能影响访问。
- “硬盘使用率”需区分容量占比和活动时间占比；“分盘”需区分物理磁盘与逻辑卷。
- 进程内存与进程 I/O 的统计口径需明确，不能默认进程数值之和等于整机用量或物理磁盘吞吐。

## 4. 决策记录

### D-001：指标覆盖与不可用处理

- 状态：已确认（2026-09-11）。
- 问题：是否接受统一界面按设备能力提供指标，对不可采集或不适用的字段明确说明原因，而不是承诺所有受支持设备都有全部读数？
- 用户结论：选择 A，跨平台覆盖优先，允许明确降级。
- 展示约定：缺失指标区分“不支持”“需要授权”“暂时采集失败”“不适用”；不展示假数据，不把缺失数据当作 0。
- 关联边界：首版基础验收目标见 D-010；能力降级不意味着原始指标清单中的所有项都可任意省略，也不代表实际安装后台服务或驱动的授权。

### D-002：目标验收设备（执行顺序已由 D-012 调整）

- 状态：目标验收设备已确认（2026-09-11）；当前仅 Mac 进入优先实施计划。
- 用户结论：Mac 使用当前开发机，Windows 使用用户截图中的电脑。D-012 将原两平台首批安排调整为先 Mac、后 Windows。

| 项目 | 当前 Mac 验收机 | 后续 Windows 候选验收机（延后） |
| --- | --- | --- |
| 信息来源 | 本机只读系统查询，用户确认 | 用户提供的系统“关于”截图 |
| 操作系统 | macOS 26.5.2（25F84） | Windows 11 专业版 25H2（26200.9445） |
| 架构 | arm64 | x64 |
| CPU | Apple M4；10 物理核 / 10 逻辑处理器，4 性能核 + 6 能效核 | AMD Ryzen AI 9 HX 370 |
| GPU | 已识别 Apple M4 集成 GPU；本次脱敏查询未取得 GPU 核心数 | AMD Radeon 890M Graphics（集成显卡） |
| 内存 | 16 GiB（17,179,869,184 字节）；统一内存架构 | 安装 64.0 GB，系统可使用容量显示为 55.6 GB；速率显示为 5600 MT/s |
| GPU 内存 | 与系统共享统一内存；实际统计接口待验证 | 系统截图显示 8 GB；预留/专用统计与动态共享的口径待验证 |
| 存储 | APPLE SSD AP0256Z，251,000,193,024 字节；外置 ZHITAI TiPlus7100 1TB，1,024,209,543,168 字节；卷布局待验证 | 截图汇总容量 2.77 TB；不能据此推断物理磁盘数量、型号或卷布局 |

- 指标解读：Windows“安装 RAM”旁的 55.6 GB 可用指系统可使用的容量，不代表当前空闲或实时可用内存；5600 MT/s 是传输速率，不应直接标成 5600 MHz 时钟频率。
- 数据最小化：不记录截图中的设备 ID、产品 ID、设备名称等非必要标识。
- 验收边界：当前 Mac 验收只依赖本机；Windows 配置保留为后续扩展基线，不作为 Mac 交付前置条件。两者均不证明其他系统版本或 GPU 已兼容。
- 采集验证：尚未在 Windows 实机执行探测，截图不能证明某项传感器或性能接口可读。

### D-003：管理员权限与增强采集

- 状态：已确认（2026-09-11）。
- 问题：是否接受基础功能以普通权限运行，用户主动授权后安装/启用独立的高权限只读采集组件？
- 用户结论：选择 A，基础模式 + 可选增强采集。
- 基础模式：普通权限运行，未授权时仍保留可用的基础功能，并对受限指标说明原因。
- 增强模式：用户主动授权后安装/启用独立的高权限只读采集组件，尝试获取更多指标；主界面保持普通权限。
- 功能边界：本阶段为只读监控，不包含调速、超频等硬件控制。
- 限制：提高权限不保证所有指标可采集；第三方内核驱动单独受 D-004 约束，增强组件的授权不能代替驱动安装授权，更不代表关闭系统安全机制的授权。
- 实施边界：这是产品权限模型的确认，不表示已在开发机安装组件、执行提权，也不代替后续实际安装时的明确授权。

### D-004：Windows 内核驱动的接受边界

- 状态：已确认（2026-09-11）；依据 D-012 暂存为后续 Windows 扩展约束，当前不实施。
- 问题：Windows 增强采集是否允许采用经过筛选、有效签名的第三方硬件监控内核驱动？
- 用户结论：选择 A，允许可选安装，但设置严格边界。
- 授权：安装驱动前单独征得用户同意；管理员采集组件的授权不能代替驱动安装授权。
- 选择条件：仅考虑来源可追溯、许可允许、维护与安全情况经过检查、签名有效且兼容当前系统安全配置的驱动。签名本身不等于安全保证。
- 安全边界：不采用已知存在未修复安全漏洞的驱动，不绕过系统拦截，不要求关闭内存完整性、安全启动或驱动签名检查。
- 降级：找不到符合条件且兼容的方案时，按 D-001 明确展示对应指标不可用。
- 技术验证：是否需要驱动、候选驱动能否支持 Ryzen AI 9 HX 370，以及实际可读字段，均尚未验证。
- 范围边界：尚未选定或安装具体驱动；此决策不自动授权 macOS 内核扩展，也不要求关闭 macOS SIP 等保护机制。

### D-005：存储“分盘展示”的组织方式

- 状态：已确认（2026-09-11）。
- 问题：总览页以物理硬盘为主，还是以盘符/逻辑卷为主展示存储状态？
- 用户结论：选择 A，以物理硬盘为主，下面列出关联逻辑卷。
- 总览：每块物理硬盘展示型号、温度、通电时间等核心硬件状态；其下列出关联卷的已用/总容量、可用容量与容量使用率。
- 详情：点击物理硬盘进入实时性能、温度历史曲线、寿命与健康等详细监控。
- 指标归属：温度、通电时间与设备健康信息归属于物理硬盘，不作为各盘符独立拥有的指标。
- 使用率语义：容量使用率与磁盘活动时间占比是两个独立指标，界面明确区分，不混用一个“使用率”标签。
- macOS：按实际磁盘、容器和卷的关系展示，共享容量不重复累计。
- 拓扑实现约束：存储池或逻辑卷可能跨越多块物理磁盘；不能为了树状展示而伪造一对一关系。复杂关系与无法可靠识别的关系需明确标注，具体交互待设计。
- 指标可用性继续遵循 D-001；本决策未承诺每块硬盘都可读取温度、通电时间或健康数据。

### D-006：历史曲线的保留方式

- 状态：已确认（2026-09-11）。
- 问题：历史曲线仅保留本次运行的数据，还是在本机持久保存、重启软件后可继续查看？
- 用户结论：选择 A，本地保存最近 7 天。
- 历史范围：CPU/GPU 占用、内存占用、磁盘读写和可读取的温度等设备/系统级时序指标；重启软件后仍可查看保留期内的记录。
- 数据粒度：近期数据保留较细粒度，较早数据降采样，以控制存储开销；具体时间档位与聚合方法待设计。
- 数据边界：历史数据仅保存在本机，不上传云端；不默认保存进程明细历史。
- 缺口：没有采集的时段明确显示为缺口，不伪装成连续记录。
- 关联决策：历史持久化不决定采集生命周期；D-007 已确认关窗继续采集、完全退出停止。
- 待设计：具体采样与降采样间隔、容量上限、过期清理和存储实现。

### D-007：关闭窗口与后台采集生命周期

- 状态：已确认（2026-09-11）。
- 问题：关闭主窗口后继续在菜单栏/系统托盘采集，还是直接退出并停止采集？
- 用户结论：选择 A，关闭窗口后继续后台监控。
- 关闭窗口：常驻 macOS 菜单栏 / Windows 系统托盘，继续采集和保存历史，重新打开窗口即可查看。
- 完全退出：菜单提供明确的“退出软件”操作，停止本应用的采集任务，不继续在后台记录。
- 开机自启：默认关闭，用户可主动开启。
- 系统睡眠：不为监控阻止系统睡眠或主动唤醒机器；睡眠期间不采集，唤醒后若软件仍运行则恢复采集，睡眠时段保留历史缺口。
- 实现边界：停止采集不等于自动卸载已安装的组件或驱动；组件退出、空闲和卸载行为需另行设计，但完全退出后不能继续暗中执行采集。

### D-008：实时刷新与后台采样节奏

- 状态：已确认（2026-09-11）。
- 问题：是否允许后台降低动态指标采样频率，以减少常驻开销？
- 用户结论：选择 A，平衡模式。
- 主要动态指标：CPU/GPU 占用、内存用量、磁盘读写速度等，在窗口显示时目标每 1 秒采样，窗口隐藏或最小化后目标每 3 秒采样。
- 取舍：后台降频减少持续采集开销，但短暂峰值更容易被平均或漏采。
- 其他指标：温度、功耗、风扇等按接口能力独立刷新，通常以 2–5 秒为目标；健康度、通电时间等低变化信息约每 60 秒；型号、SPD 等静态信息在启动或设备变化时读取。
- 用户控制：允许在设置中调整主要动态指标的前台与后台采样间隔；具体可选范围待能力和开销测试后确定。
- 真实性约束：以上为目标节奏，不保证每个来源都满足；保留实际采样时间与区间，不把旧读数反复写入历史伪装为新样本。
- 独立事项：进程明细采集策略和刷新频率尚未确定；CPU、内存、能耗与历史存储容量预算仍需实测与确认。

### D-009：进程级磁盘读写的归因范围

- 状态：已确认（2026-09-11）。
- 问题：首版提供系统范围的进程读写排行，还是进一步尝试将各进程读写归因到具体物理硬盘？
- 用户结论：选择 A，首版先做整机范围的进程读写排行。
- 展示：各进程提供读取/写入速率；每块物理硬盘仍展示自身实时读写速度。
- 范围标注：进程排行明确标注“系统范围，包含全部磁盘”，不冒充当前硬盘的专属排行。
- 首版边界：暂不把每个进程的读写进一步拆分到各块物理硬盘；不影响内存页的进程占用排行。
- 数据边界：进程明细不默认保存历史；不增加文件内容或实际读写文件路径的记录功能。
- 统计约束：进程 I/O 的含义依赖系统接口，不应假设等于物理磁盘 I/O；缓存、异步回写、系统代办 I/O 等可能导致进程统计与物理磁盘吞吐无法直接相加对应。
- 待设计项：内存排行的统计口径、应用聚合/进程展开规则、访问受限进程的展示方式，以及进程统计刷新策略。

### D-010：首版交付范围与实施顺序

- 状态：已确认（2026-09-11）。
- 问题：先交付四类硬件均有真实数据的基础可用版本，再逐步补齐高级详情；还是将原始清单中实机可采集的详情尽量集中在首版交付？
- 用户结论：选择 A，先交付基础可用版本，再补齐高级指标。
- 实施顺序：按 D-012 修订为先在本机 Mac 内完成能力验证、分阶段实现和整体验收；Windows 探测与实现延后，不阻塞 Mac。未来若启动 Windows，仍必须进行 Windows 实测，不能以 Mac 成功代替。
- 首版页面：总览、CPU/GPU/内存/磁盘详情及设置；四类硬件均需有真实动态数据，不能交付只有占位符的页面。
- 基础验收目标：CPU 总占用与每核占用；GPU 利用率与适配集显/统一内存架构的可用内存统计；系统内存总量/已用/可用；卷容量与物理磁盘读写速度。
- 基础验收处理：先验证实际口径和可用性；关键项无法实现时需向用户报告并调整验收约定，不能用“不可用”占位符冒充完成。
- 配套功能：已确认的物理盘/卷展示、进程内存与系统范围读写排行、7 天本地历史、菜单栏/托盘和前后台采样策略纳入首版。
- 优先增强：温度、通电时间、健康度等，在实机验证可读且符合权限与安全边界时优先接入。
- 后续迭代：更复杂的电压、功耗、频率细分、SPD/时序、GPU 引擎、磁盘响应时间与队列等可继续迭代，仍保留在原始需求清单中。
- 状态真实性：明确区分“尚未实现”“尚未验证”和“设备/系统不支持”，不能将开发未完成伪装成平台不支持；仍遵循 D-001 的权限、故障与不适用状态说明。
- 功能边界：D-009 已排除首版按物理盘归因的进程读写；风扇仍是可选只读监控；不引入告警、远程监控或硬件控制。

### D-011：首版使用与分发对象

- 状态：已确认（2026-09-11）。
- 问题：首版先供用户自己的两台设备使用和验收，还是计划直接向其他用户公开分发？
- 用户结论：选择 A，个人自用优先。原两台电脑共同交付的顺序已由 D-012 修订。
- 交付要求：先交付可在本机 Mac 正常安装、运行和验收的版本，不是只能通过开发命令启动；Windows 安装交付延后。
- 首版不包含：应用商店上架和自动更新。
- 后续可能性：保留正式分发的可能，选择依赖时仍检查许可。
- 共同约束：自用不等于可以绕过签名要求或降低安全标准；高权限组件、Windows 可选驱动仍遵循 D-003/D-004 的授权与安全边界。
- 未获授权事项：尚未授权购买开发者账号、证书或服务，也未授权对外发布软件。

### D-012：Mac 优先，当前仅修改计划

- 状态：已确认（2026-09-11），优先于此前两平台并行的实施与验收安排。
- 用户要求：先优先实现本机 Mac，等 Mac 全部跑通后再考虑扩展 Windows；本步骤只更改计划，暂不进入开发。
- 当前操作范围：仅修改和检查文档；不创建应用/探测代码，不运行新增采集探测、构建或应用测试，不安装依赖、注册服务、提权或安装驱动。
- 后续 Mac 路线：在获准进入开发后，按 Mac 能力验证、四类实时监控、详情与进程统计、7 天历史/菜单栏/设置、增强采集与稳定性、安装及整体验收分阶段推进。
- “全部跑通”的边界：已确认的 Mac 交付范围必须完成整体验收，不以应用能启动、少量基础读数或 M1 原型替代；基础项缺失按 D-010 报告，未实现和未验证不能冒充设备不支持。
- 保持不变：D-001 的能力降级、只读与安全边界、历史和刷新策略、D-010 的分阶段与高级指标后续迭代方式仍有效；原始指标清单不因 Mac 优先而删减，缺项及延期状态需明确列出。
- Windows 冻结范围：不开发适配器、探测脚本、服务/驱动接入、安装包或专用测试，不要求准备 Windows 构建环境，不作为 Mac 交付阻碍。
- 保留的扩展准备：仅在文档中保留平台无关指标契约、采集适配边界、设备资料与已有研究；不为 Windows 提前编写占位代码或引入专用依赖。
- Windows 启动门槛：Mac 约定范围整体验收通过并列明剩余限制后，由用户后续明确决定是否启动；不自动转入 Windows。

### D-013：用户主动结束进程（2026-09-12）

用户批准在进程排行加入普通终止操作，作为只读监控的明确例外：选择进程并二次确认后发送 SIGTERM，不提供强制结束、不提权、不安装 helper。服务端核对 PID、启动时间与当前用户身份，拒绝 PID 0/1、监控应用自身和其他用户的进程。macOS 的身份检查与发送信号无法原子执行，检查只能缩小 PID 复用竞态窗口，不能完全消除。

界面区分请求已发送、进程已退出、身份已变化和权限不足；已发送不代表目标已退出。测试只能终止专门创建的子进程，不得结束真实应用、远程控制或长期挂测实例。仍禁止触发系统休眠、硬件控制及自动上传监控数据。
