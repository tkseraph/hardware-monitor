# 硬件监控领域模型（讨论草案）

状态：产品语义已形成基线；概念结构与技术约束用于指导实施，尚非最终代码类型或数据库设计。
更新日期：2026-09-11。
关联文档：[需求与决策](requirements.md)。

D-012 调整执行顺序为 Mac 优先：本轮只维护文档，后续先完成本机 Mac；Windows 的模型语义与既有约束保留为扩展参考，不意味着现在实现适配器或 Windows 代码。

## 1. 术语与候选概念

| 概念 | 含义 | 待确认点 |
| --- | --- | --- |
| 本机（Host） | 被监控的这台计算机及其操作系统、架构 | 支持版本与设备范围 |
| 硬件设备（HardwareDevice） | CPU 封装、GPU、物理磁盘、内存模块或风扇等 | 设备身份、热插拔与多设备展示 |
| CPU 核心（CpuCore） | CPU 内可单独观测的核心/逻辑处理器 | 物理核与逻辑处理器的区别；性能核/能效核分组可用性 |
| 内存资源池（MemoryPool） | 系统物理内存、专用显存、共享/统一内存等统计对象 | 不同池可能共享物理资源，不应重复加总 |
| 内存模块（MemoryModule） | 可识别的物理内存器件及其参数 | 并非所有系统都能枚举模块或访问 SPD |
| 物理磁盘（PhysicalDisk） | HDD、SSD 等物理存储设备 | 通电时间、设备温度、磨损等指标归属 |
| 存储容器（StorageContainer） | 分区、APFS 容器、存储池等中间层 | 是否需要展示，以及如何反映共享容量 |
| 逻辑卷（Volume） | 文件系统容量和已用/可用空间的统计对象 | Windows 盘符、macOS 挂载点与“分盘”的对应关系 |
| 进程实例（ProcessInstance） | 某次启动的进程，而非永久稳定的 PID | 标识需考虑 PID 重用；程序聚合规则待定 |
| 指标定义（MetricDefinition） | 某个读数的含义、单位、统计口径和适用对象 | 百分比分母、采样窗口、单位换算 |
| 采集能力（MetricCapability） | 某个对象在当前环境下能否提供某项指标 | 支持、无权限、不适用、尚未验证等情况 |
| 指标样本（MetricSample） | 在某个时间/区间观测到的值及质量信息 | 时间戳、有效性、过期阈值与采样失败 |
| 采集来源（MeasurementSource） | 提供读数的系统接口、驱动或采集实现 | 可用性验证和多来源优先级 |
| 历史序列（MetricSeries） | 同一对象同一口径的样本集合 | 保留时长、降采样、持久化 |

## 2. 候选关系

- 本机包含多个硬件设备，也包含系统层面的资源统计。
- CPU 包含核心/逻辑处理器；GPU 可能包含多个可观测引擎。
- 物理磁盘、存储容器与逻辑卷之间不能预设为一对一；存储池和共享空间需要单独处理。
- 内存模块的硬件参数与系统内存资源池的使用统计是两类不同信息。
- 进程实例拥有资源用量样本；不能预设它们可完整归因到某个物理磁盘。
- 设备、资源池、卷、进程等监控对象通过指标定义和样本表达状态。
- 总览页与详情页应引用同一套指标语义，避免相同标签下的数值口径不一致。

## 3. 候选语义约束（待确认）

- 有效读数为 0，与无数据、无权限、不支持、不适用不同。
- “永久不支持某指标”与“本次采样失败”应区分，采集能力与样本状态不能混为一谈。
- 显示上一次有效读数时，应保留其时间信息并标识过期，不能伪装成当前实时值。
- 总占用率不应直接加总所有核心/引擎百分比；应按明确口径定义。
- 专用显存、共享显存和统一内存不能以相同名称误导展示，也不能无条件相加。
- 磁盘容量占比与活动时间占比是不同指标。
- 卷的剩余空间与物理磁盘未分配空间不同；共享存储容量不能重复累计。
- SMART 原始值、厂商寿命指标与推导健康度应标注来源和含义，不能统一假设为同一种百分比。

## 4. 已确认的产品语义

依据需求决策 D-001（用户选择 A）：

- 根据设备能力提供指标，允许明确降级。
- 缺失数据需区分“不支持”“需要授权”“暂时采集失败”“不适用”。
- 不用假数据或数值 0 替代缺失读数。
- 统一界面不等于不同平台具有完全相同的采集能力。

上述语义已确认；具体类型定义、状态转换、错误重试和过期策略尚未确定。

## 5. 首批设备对模型的约束

D-002 记录 Apple M4 Mac 和 HX 370 / Radeon 890M Windows 设备；D-012 将当前验收范围限定为本机 Mac，Windows 配置仅保留为后续扩展资料。

- 两台设备均涉及 CPU/GPU 共享物理内存；不能先假设 GPU 一定拥有独立显存，再把集显视为例外。
- 物理存储来源、操作系统报告的 GPU 内存类别、容量/预算、实际用量是不同维度；“专用”统计标签不必然代表显卡上独立的显存芯片。
- Windows 截图中的 8 GB 仅是系统报告值，预留/专用统计与动态共享的准确口径需通过实机接口验证；不得直接与系统 RAM 相加作为整机物理内存。
- 内存的安装容量、系统可使用总量、当前已用量、当前可用量和空闲量需分别定义，避免把截图中的 55.6 GB 当成实时可用内存。
- 内存传输速率（MT/s）与时钟频率（MHz）应区分。
- Windows 截图中的存储汇总容量不能替代物理磁盘与卷的拓扑探测。

这些是基于已知设备的技术语义约束；首版基础目标见 D-010，界面标签与占用率分母需按实际来源验证。

## 6. 已确认的权限边界

依据需求决策 D-003（用户选择 A）：

- 基础功能以普通权限运行，增强采集由用户主动授权后启用独立的高权限只读组件。
- 主界面保持普通权限，未授权时仍提供基础功能。
- 当前范围为监控，不包含风扇调速、超频等硬件控制。
- 管理员授权不是“全部指标可读”的保证，也不等于允许安装内核驱动。

据此提出的模型要求（具体类型与生命周期待设计）：

- 区分某指标需要的权限、用户是否授权、采集组件是否可用，以及本次样本是否有效。
- “需要授权”不能用于掩盖设备不支持、组件未安装、驱动被系统阻止或临时采集故障。
- 授权或采集组件状态变化后，应重新评估相关能力；已有读数不能无条件继续标为实时有效。
- 高权限组件只承担必要的采集职责；界面与采集组件之间的通信授权和操作范围需在实现设计中明确。

## 7. 已确认的 Windows 驱动边界

依据需求决策 D-004（用户选择 A），以下约束按 D-012 延后到 Windows 扩展阶段，当前不实施：

- Windows 增强采集可依赖可选的第三方监控内核驱动，但安装前必须单独明确授权。
- 驱动需经过来源、许可、维护、安全情况、有效签名和系统安全配置兼容性检查；不采用已知存在未修复安全漏洞的驱动。
- 不要求关闭内存完整性、安全启动或驱动签名检查，不绕过系统拦截；不符合条件时保持相关指标不可用。
- 此选择未确定具体驱动，也未授权实际安装或 macOS 内核扩展。

对能力模型的候选要求：

- 一个采集来源可能同时依赖授权、后台组件、驱动和设备兼容性；不能仅用“管理员模式已开启”推断指标可用。
- 驱动未安装、用户未授权、被安全策略阻止、设备不兼容与本次采样失败应保留不同诊断原因，供界面解释和后续验证使用。
- 驱动与后台组件的安装、启用、停用、升级、卸载及授权撤回行为需在后续设计中确定，不默认永久后台运行。

## 8. 已确认的存储展示语义

依据需求决策 D-005（用户选择 A）：

- 总览以物理硬盘为主，下面列出关联逻辑卷；温度、通电时间等属于物理设备，卷展示容量和容量使用率。
- 点击物理硬盘进入性能、温度曲线、寿命与健康等详情。
- 容量使用率与活动时间占比是不同指标，不能共用含糊标签。
- macOS 按实际磁盘、容器与卷的关系展示，共享容量不重复累计。

对应的候选实现约束：

- 页面常见形态可以是分组列表，但底层存储拓扑不能因此被限定为简单树结构；跨磁盘卷或存储池需保留多对多关系。
- 对共享容量，应明确数值归属于哪个容器/资源池；不能把多个卷各自报告的共享剩余空间加总。
- 无法确认卷与物理设备的关系时，应标明未知，不能根据盘符、挂载点或容量猜测归属。

## 9. 已确认的历史记录语义

依据需求决策 D-006（用户选择 A）：

- 设备/系统级历史仅在本机持久保存最近 7 天，不上传云端；软件重启后可继续查看保留期内的数据。
- 范围包括 CPU/GPU 占用、内存占用、磁盘读写和可读取的温度等时序指标，不默认保存进程明细历史。
- 近期数据粒度较细，较早数据降采样；具体档位、聚合方法与容量上限待设计。
- 未采集的时段明确显示为缺口。

据此提出的模型要求：

- 区分样本的采集时刻、采样区间、存储粒度和保留策略；降采样后的点不能假装为单次实时读数。
- 降采样需要区分占比、瞬时测量、吞吐速率和累计计数；不能对所有指标无差别求和或平均。
- 历史缺口、采样失败和有效数值 0 必须保留区别；不能用插值或连线掩盖未采集时段。
- 跨重启关联历史依赖稳定的设备/卷身份，不能只凭展示名称、枚举顺序或盘符连接序列。
- 历史持久化策略与采集生命周期独立；保留过去的数据不等于应用退出后继续采集。

## 10. 已确认的采集生命周期

依据需求决策 D-007（用户选择 A）：

- 关闭主窗口后保留菜单栏 / 系统托盘入口，继续采集并保存历史。
- 明确执行“退出软件”后停止本应用采集，不继续记录。
- 开机自启默认关闭，用户可主动开启。
- 不阻止系统睡眠或主动唤醒机器；睡眠期间不采集，唤醒时若软件仍运行则恢复，历史保留缺口。

据此提出的模型要求：

- 窗口可见性、应用是否运行、高权限组件是否可用、采集任务是否运行是不同状态。
- “关闭窗口”“最小化/隐藏”“完全退出”需要具有明确且跨平台可理解的行为；窗口关闭不等于采集会话结束。
- 完全退出后的采集停止与已安装组件的卸载是不同操作；不能因为组件仍安装就持续采集。
- 界面/控制进程异常退出时，高权限采集组件的任务回收与超时策略需要设计，避免失去控制后永久采集。
- 系统睡眠、唤醒和软件重启涉及采样间隔与累计计数基线重建，不能把停采时段当成有效连续采样。

## 11. 已确认的采样节奏

依据需求决策 D-008（用户选择 A）：

- 主要动态指标目标采样间隔为前台 1 秒、窗口隐藏或最小化后 3 秒，允许在设置中调整。
- 温度、功耗、风扇等传感器按接口能力独立刷新，通常以 2–5 秒为目标；健康度与通电时间等约 60 秒；型号、SPD 等静态信息启动或设备变化时读取。
- 上述为目标节奏；实际采样时间与窗口必须真实记录，不能通过重复旧值制造新样本。

据此提出的模型要求：

- 采样策略区分动态性能、传感器、低变化健康信息、静态硬件参数和进程明细，不能强制全部同频；进程明细策略尚待确定。
- 目标采样间隔、来源实际更新间隔、样本观测窗口和界面重绘间隔是不同概念。
- 调整前后台采样频率后，历史仍保留真实时间间隔；由累计计数计算速率时使用实际有效间隔。
- 不同指标如果由同一个来源批量采集，应协调调度，避免多个页面或消费者重复启动底层采集。
- 具体频率上下限、超时、背压、重试和自身资源预算待实现验证。

## 12. 已确认的进程磁盘 I/O 范围

依据需求决策 D-009（用户选择 A）：

- 首版提供系统范围的进程读取/写入速率排行，不按物理硬盘拆分归因。
- 每块物理硬盘仍展示自身读写速度；进程排行明确标注“系统范围，包含全部磁盘”。
- 该选择不影响内存页的进程占用排行；进程明细不默认保存历史，不增加文件内容或实际读写文件路径的记录功能。

据此提出的模型要求：

- 进程 I/O 样本需携带统计范围与来源，不能根据当前打开的硬盘页面改变其实际语义。
- 文件系统逻辑 I/O、物理存储 I/O、缓存命中、异步回写和系统代办 I/O 可能存在差异，进程统计之和不一定等于磁盘吞吐。
- 若后续支持按盘归因，应增加明确的归因维度与验证结果，不覆盖或悄悄改写首版系统范围指标的含义。
- 进程实时样本与设备级历史具有独立的数据范围和保留策略；进程名称不等于稳定身份，需考虑 PID 重用。

## 13. 已确认的首版范围与能力表达

依据需求决策 D-010（用户选择 A）：

- 按 D-012 修订为先在本机 Mac 验证和分阶段交付四类硬件真实动态数据、配套功能及高级指标；Mac 约定范围完成整体验收前不启动 Windows。D-010 的分阶段安排仍有效。
- 基础验收覆盖 CPU 总/每核占用、GPU 利用率与适配其内存架构的统计、系统内存用量、卷容量与物理磁盘吞吐；配套进程排行、7 天历史和运行策略不因分阶段交付而自动删除。
- 温度、通电时间、健康度等验证可读且符合安全边界时优先接入；复杂指标保留为后续目标。
- 明确区分“尚未实现”“尚未验证”“设备/系统不支持”；基础项受阻时需报告并调整验收约定，不能以全页不可用占位符宣称完成。

据此提出的模型要求：

- 产品版本是否实现某指标、采集来源是否经过验证、具体设备是否支持，以及当前样本是否有效，是不同维度。
- 实机能力验证结果关联设备/系统环境、来源、权限条件和测试时间；一台设备上的结果不能自动推广到其他设备。
- 指标的单位、适用对象、统计分母和聚合窗口需在验收前明确，不能只按名称判断两个平台是否实现了相同功能。
- 分阶段交付调整实现顺序，不删除原始指标目标；实际平台验证与构建成功是不同证据。

## 14. 从概念模型到实施契约

D-011 确认个人自用、不做商店上架或自动更新；D-012 将当前交付收敛为本机 Mac，Windows 延后。发布顺序不改变指标语义、权限或驱动安全边界；只保留必要平台适配边界，不提前编写 Windows 空实现。

建议按三个业务边界组织实现，暂不引入微服务：

1. **设备与观测**：硬件清单、存储拓扑、指标定义、能力判断和样本。
2. **采集运行**：前后台策略、权限、来源依赖、任务生命周期与故障恢复。
3. **历史与展示**：设备级留存、降采样、范围查询、缺口与页面投影。

建议的核心契约（工程草案，不是已实现类型）：

| 契约 | 必需信息 |
| --- | --- |
| `MetricDefinition` | 指标 ID/版本、对象类型、单位、统计范围、方法、百分比分母、聚合规则 |
| `MetricCapability` | 实现覆盖、验证状态、支持状态、权限/组件依赖、原因与证据 |
| `MetricSample` | 对象 ID、指标版本、来源、观测时间与区间、值或质量状态、来源代次 |
| `StorageTopology` | 物理设备、容器、卷及关联关系；容量所属资源池；关系置信/验证状态 |
| `ProcessInstance` | 启动会话、PID、启动标记；无法可靠识别重用时不跨样本续接差分 |
| `CollectorSession` | 运行状态、订阅需求、目标采样策略、授权状态、受控任务与会话租约 |
| `HistoryBucket` | 覆盖区间、有效覆盖时长、聚合方法、数量、极值与缺口信息 |

实现约束：

- 传感器身份不等于显示名称；指标口径或来源切换必须保留来源代次/版本信息，不能静默拼接历史。
- CPU/GPU 差分与速率使用单调时钟计算有效间隔；持久化另存可展示的墙上时间及采集会话标记，处理系统时间跳变。
- Rust 中的字节累计计数采用足够宽的整数；跨 WebView 边界不让超出 JavaScript 安全整数范围的数值悄悄失真，DTO 明确使用十进制字符串或经验证的安全数值。
- 权限/实现覆盖/能力与采样质量分开，避免一个不断膨胀的枚举同时表示互相独立的状态。
- 采样状态至少处理预热、有效、过期、失败和重置；非有效值不使用 NaN 或 0 穿透到正常读数。
- `GPU 内存预算` 不等于 `物理显存容量`；进程级 GPU 内存不等于整机 GPU 用量。
- Windows `GetProcessIoCounters` 文档定义为进程全部 I/O，不能未经验证标成纯磁盘 I/O；见 [能力矩阵](capability-matrix.md)。
